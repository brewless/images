# Changelog

## Not released yet

- A new PHP minor becomes available by itself (BL-305). The PHP versions are listed once, one per line, in `php-versions`; the build matrix, `scripts/php-releases.sh` and `scripts/scan-images.sh` read it. Every hour `runtime-updates.yml` looks for the minor after the newest line (8.7 after 8.6) and for the next major's first (9.0). Once Docker Hub's `dunglas/frankenphp` has a stable `1-php<minor>.<n>` tag for one (no alpha, beta or RC), it is appended to `php-versions`, the Dockerfiles' version check gets it as its newest version (the previous newest moves into the map with the minimum it had), and the commit, `feat: PHP 8.7 available`, publishes its images. The webhook to Brewless names the new minors in `new_versions`.
- Security updates reach the images by themselves (BL-303). `.github/workflows/runtime-updates.yml` runs every hour (and by hand, also from the Brewless admin panel): it compares the newest FrankenPHP release per PHP version with the one in `brewless-base` and scans every published image with Trivy (pinned, `aquasec/trivy:0.58.1`). A newer PHP release, or a CRITICAL or HIGH finding with a fix that was not rebuilt for yet, raises the minimum in the Dockerfile, updates the realtime image's Composer packages and version where needed, and publishes. `brewless-base` upgrades its Debian packages and `brewless-realtime` its Alpine packages when they are built. After publishing, `publish.yml` calls Brewless's webhook (`BREWLESS_IMAGES_WEBHOOK_URL` and `BREWLESS_IMAGES_WEBHOOK_SECRET`, both repository secrets, so the public logs never show them) with the realtime version and the fixed vulnerabilities, signed over its moment and body; every run also reports its scan. The watch covers PHP 8.3 to 8.6 and reads the minimum of each version from the Dockerfile, whether it is in the map or the fallback after `??`.
- `brewless-builder` carries `openssh-client` (`ssh`, `ssh-keygen`, `ssh-keyscan`), so a job in the customer's project can fetch a private repository with a read-only deploy key.
- The build pipeline is tightened. A pull request only builds the images, with a token that may read the repository and nothing else; before, its token could write packages. Only `main` is published, also when the workflow is started by hand from another branch. The checkout leaves no token in `.git`, and `.dockerignore` keeps `.git` out of the build context.
- The tools `brewless-builder` copies from other images (Composer, Node, crane, rclone) are taken by digest, as pgloader was, and crane by release (v0.22.1) instead of `latest`. Dependabot proposes a new digest or commit when one of them, or an action, is released. The FrankenPHP image the base starts from still follows its tag on purpose, so a rebuild picks up a patched PHP.
- `brewless-realtime`: Composer installs the packages without running their scripts or plugins, so no code of a package runs before its licence was checked; Laravel's package discovery is run by name afterwards. Takes effect with the next version of the image.
- What the build downloads is checked before it is used: the source of phpredis for the 8.6 image and the key of the PostgreSQL repository in `brewless-builder` are compared with a SHA-256 in the Dockerfile, and the build stops when one differs. The GitHub Actions of the publish workflow are taken by commit, not by tag.
- PHP 8.6: `brewless-base` and `brewless-builder` are published for `php8.6` too, on FrankenPHP's `1-php8.6` image (PHP 8.6.0 of 19 November 2026), with the same extensions as the other versions. Two things differ underneath. The released `redis` extension (6.3.0) does not compile on PHP 8.6, so the 8.6 image builds it from the commit of phpredis's development branch that phpredis tests on 8.6 (`PHPREDIS_FOR_PHP_86` in the Dockerfile), until a release does. And PHP's own 8.6 image no longer has `mbstring` compiled in, so the build adds it. The build refuses an 8.6 older than 8.6.0 and an image without `redis` or `mbstring`. Without `PHP_VERSION` the Dockerfile still builds for 8.4. `brewless-realtime` 1.2.0 carries the same refusal for 8.6 and still runs on PHP 8.4.
- PHP 8.3.37, 8.4.28 and 8.5.13, the security release of 19 November 2026 (CVE-2026-115560 among its fixes); the build of `brewless-base`, `brewless-builder` and `brewless-realtime` refuses an older PHP. `brewless-realtime` 1.1.1 carries it.

- `brewless-base` (and so `brewless-builder`) carries the `uv` extension. A realtime server on an application's own image (Laravel Reverb) holds its connections with libuv instead of `stream_select`, which stops at 1,024 open files. Measured on a Scaleway Serverless Container: without `uv` the server stopped at connection 1,018 and every browser was cut.
- `brewless-realtime` 1.1.0 carries the `uv` extension (0.3.1) for the same reason. With it a 256 MB container at Scaleway held about 1,300 connections that only listened. `REVERB_APP_MAX_CONNECTIONS` now counts every open connection, not only the ones that joined a channel, and the connection that is one too many is closed with Pusher code 4004 instead of being left open after the error. Brewless sets that ceiling from the container's memory.
- `brewless-base` (and so `brewless-builder`): a static file under `public/` asked for with its version in the query string (`/img/logo.svg?v=1a2b3c`, as an application's asset helper writes it) gets `Cache-Control: public, max-age=31536000, immutable`, like `/build/*` already did. A page with `?v=` and a file that does not exist are left alone. Before this, such files had no `Cache-Control` at all on the container's own address and on the test address, and PageSpeed flagged them.
- `brewless-realtime` 1.0.0, a new image: a bare Laravel 13 application on PHP 8.4 (Alpine) that runs Laravel Reverb 1.12 on its own for one application, configured with `REVERB_APP_ID`, `REVERB_APP_KEY`, `REVERB_APP_SECRET` and `REVERB_ALLOWED_ORIGINS`. A stop closes every connection with Pusher code 4200 so clients reconnect at once, and a connection from a refused origin is closed with 4009. Published as `brewless-realtime:1.0.0`, `:1.0` and `:1`; a published version is never replaced. The build refuses a package that is not under a permissive licence.

## 1.0.0 (4 November 2026)

First tagged release. The images have been building and running Brewless's own
site and its customers' applications since October; this gives that state a
version to point at. What is in it:


- `brewless-builder` carries the PostgreSQL 18 client from apt.postgresql.org (its `pg_dump` reads every server up to 18), the MariaDB client (`mariadb-dump`, which also reads MySQL) and `pgloader` from `ghcr.io/dimitri/pgloader` (the Debian build cannot sign in to MySQL 8), for `brewless db:import`. Its `/etc/mysql/my.cnf` holds only `[client]`: pgloader cannot read `!includedir`.
- `brewless-builder` carries `rclone` 1.75.2, for `brewless storage:import` (copying an existing S3 bucket into the application's bucket).
- `brewless-base` (and so `brewless-builder`) carries `postgresql-client` (`pg_dump`, `pg_restore`) and `poppler-utils` (`pdftotext`) from Debian.
- PHP 8.3.36, 8.4.27 and 8.5.12 (FrankenPHP images of 2026-10-21), which fix PHP2Shell; the build refuses an older PHP. `memory_limit` is back to 256M.
- `session.upload_progress.enabled` is off, `session.use_strict_mode` on and `fatal_error_backtraces` off by default, as a mitigation for PHP2Shell (CVE-2026-109618 and CVE-2026-109619).
- `brewless-base` and `brewless-builder` for PHP 8.3, 8.4 and 8.5 on FrankenPHP 1.
